Architecture

Distributed Control Plane Design

Ginni Hema Sundara Rao Managed ArgoCD Platform  •  Checkpoint 2 4 / 9
This is the full architecture. Let me walk you through each layer. [Step 1] The user interacts with the Routing Service — a Spring Boot application — via REST API to onboard clusters, projects, and applications. [Step 2] The Routing Service stores all user-owned state in PostgreSQL: who owns what, which partition it belongs to, which control plane it's assigned to. [Step 3] Managed ArgoCD is the unified experience — it uses the ApplicationSet Plugin Generator to call the Routing Service and get back the list of resources for each partition. [Step 4] Under Managed ArgoCD are independent control planes — CP-1, CP-2, CP-N. Each one is a full ArgoCD instance with its own reconciliation scope. [Step 5] Each CP manages a bounded set of user clusters. CP assignment lives in the database, not in Git. That's the key to zero-churn failover. Git holds the platform configuration — ApplicationSet specs and Helm chart values. PostgreSQL holds the user state.
Partitioning Model

Bounded Reconciliation at Any Scale

Ginni Hema Sundara Rao Managed ArgoCD Platform  •  Checkpoint 2 5 / 9
The partitioning model is what makes this system horizontally scalable without runaway reconciliation cost. [Step 1] Without partitions: one ApplicationSet watching all 200,000 applications. Every change anywhere triggers a full rescan. At this scale, that means OOM risk and slow sync loops. [Step 2] With partitions: a top-level platform ApplicationSet generates partition-level ApplicationSets. Each partition ApplicationSet is scoped to roughly 100 apps. [Step 3] We can zoom into partition-0042 — it sees exactly its ~100 apps. Nothing more. [Step 4] The critical property: partitions are stable. An app is assigned to a partition once, permanently, by a stable hash. If you delete an app from partition-0042, only partition-0042 rescans. All other 1,999 partitions are completely unaffected. No rebatching. No churn. Reconciliation cost stays bounded at O(partition-size) regardless of total fleet size.
Failover

Control Plane Failover — Two DB Rows

Ginni Hema Sundara Rao Managed ArgoCD Platform  •  Checkpoint 2 6 / 9
The failover story is the clearest demonstration of the architectural separation we've built. [Normal] We start with cluster-001 and cluster-002 assigned to CP-1, and cluster-003 on CP-2. All healthy. [Step 1] CP-1 goes down. cluster-001 and cluster-002 are now unmanaged. Applications on those clusters are stalled. [Step 2] The failover operation: two database rows. UPDATE clusters SET control_plane_id = 'cp-2' WHERE name IN ('cluster-001', 'cluster-002'). That's it. No Git changes. No ApplicationSet edits. No partition reassignment. [Step 3] The Routing Service API now resolves cluster-001 and cluster-002 to CP-2. Managed ArgoCD's ApplicationSet plugin generator picks this up on next reconcile. [Step 4] All applications are now reconciling via CP-2. Partition memberships are completely unchanged — there was nothing to change. The partition identities live in the database as stable assignments, not derived from which CP is running. This is the key insight: control plane assignment and partition membership are orthogonal. Failover is a routing concern, not a partitioning concern.
