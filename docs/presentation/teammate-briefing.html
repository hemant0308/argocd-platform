Architecture Stack

A central Managed ArgoCD orchestration layer sitting in front of multiple ArgoCD control planes. Users interact only with the Routing Service; they never talk to a CP directly.

          User
            │  REST API
            ▼
     ┌─────────────────┐
     │  Routing Service │  Spring Boot — argocd-platform-service
     │  (PostgreSQL)    │  Source of truth for all user state
     └────────┬────────┘
              │  Plugin Generator callbacks
              ▼
     ┌──────────────────┐
     │  Managed ArgoCD  │  Central orchestrator (GitOps for infra)
     └──┬───────┬───────┘
        │       │        │
        ▼       ▼        ▼
      CP-1    CP-2      CP-N     ← ArgoCD Helm installs, Git-managed
        │       │        │
        ▼       ▼        ▼
     User Clusters (deployed workloads)
Platform-owned state
Git: bootstrap, CP Helm values, platform ApplicationSets, charts
User-owned state
PostgreSQL: users, projects, clusters, applications, partitions, CP assignment
Key invariant: User applications, projects, and clusters are never manually maintained in Git. All user mutations flow through the Routing Service API → PostgreSQL → ArgoCD reconciliation cycle.

Application name uniqueness

Service appends a 5-char lowercase hex suffix at creation: my-app → my-app-3f2a1. Global unique constraint on applications.name. Suffix is returned in create response — callers must store it.

Bootstrap — Managed ArgoCD Installation

The platform itself is bootstrapped via a single App-of-Apps entry point committed to Git. Managed ArgoCD manages its own platform ApplicationSets through this bootstrap.

Entry point

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: argocd-platform
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/hemant0308/argocd-platform.git
    targetRevision: main
    path: argocd/managed       # Helm chart containing platform AppSets
  destination:
    server: https://kubernetes.default.svc
    namespace: argocd
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
  1. Bootstrap Application is applied once manually (or via CI) to Managed ArgoCD's cluster
  2. It points to argocd/managed — a Helm chart that declares all top-level ApplicationSets (CP, project-partitions, cluster-partitions, application-partitions)
  3. From this point forward, all platform AppSet changes go through Git → ArgoCD self-heal. No manual kubectl needed.
Managed ArgoCD manages itself. The platform is fully GitOps from day 1 — including the control-plane installations.

Control Plane Provisioning

New ArgoCD control planes are provisioned automatically by Managed ArgoCD itself via a Cluster Generator ApplicationSet. No manual Helm installs needed once a cluster is labelled.

Cluster Generator AppSet

# managed/applicationsets/control-planes.yaml
generators:
  - clusters:
      selector:
        matchLabels:
          argocd-platform/control-plane: "true"

For each cluster matching this label, Managed ArgoCD generates and syncs one Application that installs the argo-cd Helm chart:

Common values

control-planes/values/default.yaml

Notification triggers, ArgoCD base config, resource limits shared by all CPs

Per-CP override values

control-planes/values/cp-1/default.yaml

CP-specific ingress, auth, node selectors, scaling config

To add a new CP: register the K8s cluster in Managed ArgoCD with the label argocd-platform/control-plane: "true" → Managed ArgoCD automatically creates + syncs an Application that installs ArgoCD on it.

Git vs PostgreSQL Responsibility Split

Git owns (platform-layer)
  • Managed ArgoCD bootstrap
  • CP Helm values (common + per-CP)
  • Platform ApplicationSet definitions
  • Helm charts (project-partition, cluster-partition, application-partition, application-registration)
  • Notification trigger/template config
PostgreSQL owns (user-layer)
  • User accounts + project memberships
  • Projects + cluster assignments
  • Clusters + CP assignment (control_plane_id)
  • Applications + Git sources (JSONB — schema-free)
  • Partition assignments (stable FK, never recalculated)
  • Resource status lifecycle

The 3-Level ApplicationSet Rule

Critical ArgoCD constraint: An ApplicationSet cannot create another ApplicationSet directly. The hierarchy must alternate: AppSet → App → AppSet → App.
AppSet (Level 1) ← Plugin Generator: partition discovery └── App (Level 2) ← deploys a Helm chart that contains the child AppSet └── AppSet (Level 3) ← Plugin Generator: group/member query for this partition └── App / Resource (Level 4) ← actual user resource

This 3-level structure is applied identically to all four resource pipelines: control planes, projects, clusters, applications.

Control Planes Pipeline — Cluster Generator

Unlike the other 3 pipelines, control plane management uses the Cluster Generator (not Plugin Generator). It operates at 1 level (no partitioning needed).

control-planes-appset [Cluster Generator — label: argocd-platform/control-plane=true] ├── control-plane-cp-1 [App] → installs argo-cd Helm chart on CP-1 cluster ├── control-plane-cp-2 [App] → installs argo-cd Helm chart on CP-2 cluster └── control-plane-cp-N [App] → installs argo-cd Helm chart on CP-N cluster
⚠️
Auto-prune is disabled on this AppSet. Removing a CP from the registry must go through a deliberate drain → remove workflow. Auto-pruning would cascade ArgoCD removal to all child workloads — catastrophic blast radius.

Projects Pipeline — 3-Level Plugin Generator

project-partition-appset Plugin Generator → POST /api/v1/getparams.execute resource=project-partitions Returns: [{partitionNumber:1, controlPlanes:[cp-1,cp-2,cp-3]}, ...] │ ├── project-partition-01 [App] → charts/project-partition, helm.valuesObject.partition=01 │ └── project-partition-01-appset │ Plugin Generator → resource=project-groups partitionNumber=01 │ Returns: [{controlPlane:cp-1, projects:[{name,clusters:[...]}]}, {controlPlane:cp-2,...}] │ ├── project-01-cp-1 [App] creates AppProject on CP-1 │ ├── project-01-cp-2 [App] creates AppProject on CP-2 │ └── project-01-cp-N ... (AppProjects fan out to ALL CPs) │ └── project-partition-02 ... same structure
ℹ️
Why fan out to all CPs? AppProjects must exist on every CP because any application partition can route to any CP. A project created once in PostgreSQL must have a corresponding AppProject on all CPs before any application can be assigned to clusters on those CPs.

project-groups response shape

{
  "partitionNumber": 1,
  "controlPlane": "cp-1",
  "projects": [
    {
      "name": "payments",
      "clusters": [
        { "name": "cluster-001", "namespaces": ["payments-prod"] }
      ]
    }
  ]
}

spec.destinations on the AppProject are generated from this cluster list — not statically configured in Git.

Clusters Pipeline — 3-Level Plugin Generator

cluster-partition-appset resource=cluster-partitions → [{partitionNumber:1,...}, {partitionNumber:2,...}] │ ├── cluster-partition-01 [App] → charts/cluster-partition, partition=01 │ └── cluster-partition-01-appset │ resource=cluster-groups partitionNumber=01 │ Returns elements grouped by CP: clusters targeting CP-1, clusters targeting CP-2 │ ├── cluster-group-01-cp-1 [App] deploys cluster registration secrets on CP-1 │ └── cluster-group-01-cp-2 [App] deploys cluster registration secrets on CP-2 │ └── cluster-partition-02 ... same

The cluster-groups response groups clusters by their control_plane_id. The auth JSONB from the clusters table is passed verbatim to the cluster-registration Helm chart, which generates the ArgoCD cluster Secret.

Applications Pipeline — 3-Level Plugin Generator

application-partition-appset resource=application-partitions → [{partitionNumber:1,...}, {partitionNumber:2,...}] │ ├── application-partition-0001 [App] → charts/application-partition, partition=0001 │ └── application-partition-0001-appset │ resource=application-groups partitionNumber=0001 │ Returns: [{controlPlane:cp-1, applications:[{name,project,cluster,sources}]}] │ ├── my-app-3f2a1 [App] destination: https://cp-1-argocd.internal → routes to CP-1 │ ├── checkout-a92b3 [App] destination: https://cp-2-argocd.internal → routes to CP-2 │ └── ... │ └── application-partition-0002 ... ~100 apps per partition
Routing via destination server: Managed ArgoCD creates the Application; the destination.server points to the CP's ArgoCD. The CP then reconciles the actual K8s workload on the user's cluster. Managed ArgoCD never touches the user cluster directly.

application-groups response shape

{
  "partitionNumber": 1,
  "controlPlane": "cp-1",
  "applications": [
    {
      "name": "my-app-3f2a1",
      "project": "payments",
      "cluster": "cluster-001",
      "sources": [{ "repoURL": "...", "revision": "main", "path": "deploy" }]
    }
  ]
}

sources is the raw JSONB from the DB. Any ArgoCD source shape works (single, multi-source, Helm, Kustomize) without schema changes.

Plugin Generator API Reference

All ArgoCD-facing data APIs use the Plugin Generator protocol: POST /api/v1/getparams.execute with a resource parameter.

resource valueLevelReturnsExtra params
project-partitions L1 All partition descriptors + controlPlanes list (for fan-out) —
project-groups L3 Projects per CP for a specific partition, with cluster assignments partitionNumber
cluster-partitions L1 All cluster partition descriptors —
cluster-groups L3 Clusters per CP for a specific partition, including auth JSONB partitionNumber
application-partitions L1 All application partition descriptors —
application-groups L3 Applications per CP for a specific partition, with sources partitionNumber
ℹ️
No List Generator used. The Plugin Generator returns actual partition descriptors (not a count). ApplicationSet creates one App per returned element — no numeric expansion primitive needed.

Partition ≠ CP assignment. Failover moves apps between CPs without changing partition membership.

Stable Partition Assignment

⚠️
Never dynamically rebatch. Sorting all resources and dividing every N causes unrelated resources to change partitions on every add/delete → massive unnecessary AppSet churn.

Assignments are persisted as FKs in the DB. When a resource is deleted, its partition shrinks but the other resources don't move. A new partition is created only when all existing partitions hit the configured target size.

// Wrong — rebatching
sort(all_apps) → take every 100 → recalculate

// Correct — stable FK
app-001.application_partition_id = 1  (set at creation, never changes)
app-050 deleted → partition-01 now has 99 members, no other app moves

The generation column on partition tables lets ArgoCD detect that a partition's content changed without fetching all members.

Redis Partition Cache ✅ Built

At steady state, most Plugin Generator calls return unchanged data. Re-querying PostgreSQL on every ArgoCD poll cycle across 2000 partitions creates unnecessary DB load.

Implementation

ComponentRole
PluginCacheServiceCaches Plugin Generator responses per (resource, partitionNumber) key in Redis. Configurable TTL (default 5 min). TTL is safety net only — explicit invalidation is the primary mechanism.
CacheInvalidationListenerListens for PartitionChangedEvent (Spring ApplicationEvent). On receipt, evicts the affected (resource, partitionNumber) key from Redis immediately.
ArgoCDRefreshListenerListens for the same PartitionChangedEvent. After cache eviction, triggers an immediate ArgoCD Application refresh via the ArgoCD API so the next poll cycle gets fresh data without waiting for the poll timer.

Cache key

partition-cache:{resource}:{partitionNumber}
# e.g.
partition-cache:application-groups:0001
partition-cache:project-groups:01

Opt-in

CACHE_ENABLED=true   # env var — default false in local dev
✅
Caching is transparent to ArgoCD. The Plugin Generator endpoint checks Redis first; on miss it queries PostgreSQL and populates the cache. ArgoCD never knows the difference.

requeueAfterSeconds config ✅ Built

Independently configurable per resource type in argocd/managed/values.yaml. Changes propagate to all Level-1 and Level-2 AppSets via Helm valuesObject.

Application Deletion State Machine ✅ Built

SOFT_DELETE: exclude from plugin response → ArgoCD prunes App → K8s resources retained

Identity and RBAC Boundary

The platform uses a split authorization model: Routing Service enforces platform-level access; control-plane AppProjects enforce ArgoCD resource policy.

LayerEnforcesHow
Routing Service Platform authorization — can this user operate on Project X? project_members table lookup before any write
Control-plane AppProject ArgoCD resource policy — what can apps in this project do? clusterResourceBlacklist, destination restrictions, sourceRepos

Why the split?

When Managed ArgoCD creates Applications/ApplicationSets on a CP, it uses its own service account (system:serviceaccount:kube-system:argocd-manager) — not the initiating user's identity. User-level RBAC in ArgoCD is therefore bypassed entirely. The Routing Service is the only place where user identity is checked.

Project-Level Resource Blacklisting

Since all Applications and ApplicationSets on CPs are created by Managed ArgoCD's service account, users who have ArgoCD UI/API access to their project could — without additional guards — directly create or modify ArgoCD lifecycle resources within their project, bypassing the Routing Service entirely.

⚠️
The problem: ArgoCD project RBAC controls who can create Applications in a project. But Managed ArgoCD's service account is the actor — not the end user. The end user's ArgoCD role doesn't apply to creation operations performed by the platform.

The fix — AppProject resource blacklisting

When Managed ArgoCD provisions an AppProject on a CP (via the project-registration Helm chart), it injects a platform-enforced resource blacklist that blocks users from directly creating ArgoCD CRDs inside their project:

# Applied at chart generation time — platform-enforced, not user-configurable
clusterResourceBlacklist:
  - group: "argoproj.io"        # blocks Application, ApplicationSet, AppProject
    kind:  "*"
  - group: "apiextensions.k8s.io"  # blocks CRD creation
    kind:  "CustomResourceDefinition"
Result: A user accessing their project in ArgoCD UI/API cannot create Applications, ApplicationSets, or AppProjects directly. All resource lifecycle operations must go through the Managed ArgoCD API → Routing Service → PostgreSQL → reconciliation cycle.

Two-tier model (§32.13)

Tier 1 — Platform defaults (Git)
Defined in Helm values. Merged into every AppProject at reconciliation time. Cannot be overridden by users. Changing a default rolls out to all projects on next sync — no DB migration.
Tier 2 — User-provided spec (PostgreSQL)
Users may add additional AppProject spec via platform API (stored as spec JSONB on projects table). Platform blacklists are always unioned in — user cannot remove them. Allowed user additions: sourceRepos, roles, syncWindows.
ℹ️
destinations are never user-configurable — always derived from project_clusters at reconciliation time. Adding a cluster to a project in the DB is the only way to add a destination.

Failover Model

Control-plane assignment lives on clusters.control_plane_id. Applications derive their CP transitively via their cluster. No control_plane_id on the applications table.

-- CP-1 fails. Two DB updates move 200 clusters:
UPDATE clusters
SET    control_plane_id = 'cp-2'
WHERE  control_plane_id = 'cp-1';
Before failover: cluster-001 → CP-1 cluster-003 → CP-2 app-001, app-002 in application-partition-01 After failover (DB update only): cluster-001 → CP-2 cluster-003 → CP-2 app-001, app-002 still in application-partition-01 (partition unchanged) Next AppSet reconcile: application-partition-01-appset calls application-groups → Routing Service joins application → cluster → control_plane → returns CP-2 as destination → Managed ArgoCD moves app-001, app-002 to CP-2

Zero churn on partition

Application partition membership does not change during failover. The AppSet identities (application-partition-0001, etc.) remain stable. Only the destination.server on the generated Applications changes.

ℹ️
Controlled Failover API (§32.10 — TODO): Planned API will wrap the raw DB update with stepping (single-switch or batched), label/name filters, dry run, async + operationId progress tracking, and cancel support.
