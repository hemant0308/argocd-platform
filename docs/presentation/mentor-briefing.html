The Problem

Why the current setup cannot scale further
14 nodes

At the Scaling Ceiling

The existing ArgoCD deployment has been scaled to 14 nodes. Performance and reliability degrade further beyond this point — the architecture has reached its practical limit.

1 failure domain

Single Point of Failure

All applications, clusters, and consumers share a single ArgoCD instance. An issue in one area — a rogue workload, a misconfiguration, a surge — can impact everything else on the platform.

8× target scale

Target: 2,000+ Clusters

The platform needs to grow from ~250 clusters to 2,000+ and from ~3,100 applications to 200,000+. The current architecture cannot absorb this growth without a fundamental redesign.

💡
The root constraint is architectural, not operational. Adding more nodes to a single ArgoCD instance shares the same Redis, etcd, and failure domain — it does not eliminate the blast radius or unlock true horizontal scale.
🏗

Our Approach

One unified API. Many independent control planes.

Instead of scaling one giant ArgoCD, we introduce a Managed ArgoCD orchestration layer that routes work across multiple independent ArgoCD control planes — each with its own failure domain, its own operational scope, and its own scaling ceiling.

Users interact with a single API. They never know — or need to know — which control plane their application lives on. The platform manages routing, partitioning, failover, and reconciliation automatically.

✓

How It Solves Each Problem

Five design decisions, five problems addressed
Scale

Horizontal Control Plane Distribution

Scale is no longer a function of one ArgoCD instance's capacity. New control planes are added as needed — each independently sized, independently operated. The platform routes work across them automatically with no change to user-facing APIs.

Blast Radius

Isolated Failure Domains

A degraded or overloaded control plane affects only the clusters assigned to it. Other control planes and their workloads continue running. Failures are contained by design, not by luck.

Infra Reliability

Pure GitOps — Control Planes as Code

Control planes are not manually installed or configured. Managed ArgoCD provisions them automatically when a cluster is registered with the platform label. Every control plane is reproducible from Git in minutes.

Resilience

Fast, Safe Failover

Moving all clusters off a failed control plane requires a single database update — no manual reconfiguration, no Helm overrides, no downtime window. The platform detects the change and reconciles automatically. Full and partial failover are both supported, with stepping and progress tracking.

Operational Cost

Stable Partitioning — No Resource Churn

Applications are assigned to stable partitions at creation time. Adding or removing a resource never triggers a global rebalance — unrelated workloads are not touched. Reconciliation work stays scoped to what actually changed.

Propagation Speed

Event-Driven State Propagation

When a user registers an application or moves a cluster, the platform immediately triggers reconciliation of only the affected partition — not waiting for the next polling cycle. Polling remains as a safety net only.

What We've Built

Capabilities delivered in this phase

Platform Backbone

✓ Full REST API for managing projects, clusters, and applications
✓ PostgreSQL data model — partitions, CP assignment, resource lifecycle
✓ Plugin Generator integration — dynamic routing without static configuration
✓ Application name uniqueness enforced globally with stable identifiers
✓ Cluster-project authorization enforced at the service layer

GitOps Infra Layer

✓ Self-bootstrapping platform — Managed ArgoCD manages itself via Git
✓ Automated control plane provisioning from a cluster label — no manual Helm installs
✓ Per-control-plane configuration overrides, version-controlled in Git
✓ Separate poll cadences per resource type — tunable without code changes
✓ AppProject destinations auto-generated from cluster assignments — no manual Git edits

Performance & Consistency

✓ Redis partition cache — eliminates redundant DB reads at steady state
✓ Cache explicitly invalidated on every state-mutating write
✓ Immediate ArgoCD refresh triggered after cache invalidation
✓ Stable partition assignment — deletions never cause rebalancing

Observability & Safety

✓ Live ArgoCD state reflected in platform DB — sync, health, degraded, error
✓ Notification pipeline from ArgoCD to platform service — no polling required
✓ Safe application deletion — two modes: retain K8s resources or cascade-delete
✓ Controlled failover API — full or partial, stepped batches, dry run, async progress
✓ Resource blacklisting on AppProjects — prevents privilege escalation
